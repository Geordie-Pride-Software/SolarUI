Separate UI Screens

SolarUI can be organised into separate UI screens so that only the controls belonging to the active screen are updated and drawn. This is useful for main menus, settings, pause menus, game HUDs, login pages, and other distinct interfaces.

Recommended design: Treat a screen as a group of UI elements. The application switches the active screen instead of manually hiding and showing every element.

Example screen layout

Main Menu
 ├── Play
 ├── Settings
 └── Exit

Settings
 ├── Volume
 ├── Fullscreen
 └── Back

Game
 ├── Score
 ├── Pause
 └── ...

Screen API

solScreen mainMenu;
solScreen settings;
solScreen game;

solScreen_Init(&mainMenu);
solScreen_Init(&settings);
solScreen_Init(&game);

Elements are associated with a screen:

solScreen_AddElement(&settings, &volume.Element);
solScreen_AddElement(&settings, &fullscreen.Element);
solScreen_AddElement(&settings, &back.Element);

The active screen can then be selected:

solUI_SetScreen(&settings);

After switching screens, the normal frame loop remains unchanged:

solUI_Update();
solUI_Draw();

SolarUI operates on the currently active screen.

Screen switching from callbacks

void OpenSettings(void)
{
    solUI_SetScreen(&settings);
}

void BackToMenu(void)
{
    solUI_SetScreen(&mainMenu);
}

Screen history

For applications that need browser-like navigation, a screen history can be maintained so the application can return to the previous screen.

solUI_SetScreen(&settings);
solUI_GoBack();
Implementation note: The screen system should own the grouping/navigation logic; individual UI elements remain normal SolarUI elements. This keeps the element API unchanged while allowing complete interfaces to be swapped as a unit.
